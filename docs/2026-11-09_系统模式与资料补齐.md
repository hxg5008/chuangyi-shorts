# 系统模式与角色资料补齐（2026-11-09，v4.4）

本文说明本轮新增的表现类型、系统界面形象和资料检查流程，供使用、验收和后续开发交接。代码位于 `huobao-source-20261109-platform-v4`，沿用现有工作树；本轮没有在用户生产服务部署，没有读取或修改真实账号、项目、Cookie、Key 和作品。真实付费模型请求为 **0**。

## 1. 解决的问题与使用边界

此前部分角色已经有图片和完整最终提示词，但结构化样貌／妆造为空；有台词的角色也可能没有声线卡。含“宿主／任务／奖励”等设定的剧本中，“系统”可能被当成普通人物，走真人形象出图流程。

本轮增加两项相互配合、边界不同的能力：

- **角色资料检查与定向补齐**：检查已关联角色的资料与本集原文，有依据才补空字段；不重画已采用图片、不把原提示词清空。
- **项目系统模式**：用户明确开启后，区分普通人物、系统界面、具体化身、仅声音和待确认。系统仍保留角色身份与声线；无实体系统的视觉参考可以是一张统一界面图。

普通模式是默认值。普通短剧不会因为角色名包含“系统”、样貌为空或者本轮更新而自动启用系统模式。医院系统、系统管理员、手机系统等字样，不足以识别为宿主系统。

“原规则保护”不代表程序完全没有增加行为：原 28 份 Skill 文件、16 份系统提示词文件，以及 20 个 Agent 工具输入 Schema 和 2 个主要分镜 Schema 保留原文；本轮**确实增加了资料检查／补齐模型调用，以及系统模式下的分类、专用设计、参考图选择和条件校验逻辑**。新增指令存放在独立服务模块中，未写回原 44 份模板。普通项目不进入系统专用分类与界面分支，但原提取后的通用缺项检查／定向补齐会执行。

## 2. 使用顺序

1. 普通剧本保持“普通模式”，按原流程提取角色、场景和道具。
2. 有宿主系统设定的项目，在项目详情或单集资产制作中的“剧本模式 → 设置”明确选“系统模式”。保存设置本身不调用模型。
3. 正常提取资产。新增的已保存角色会结合本集完整剧本识别表现类型；单集与多集批量共用后端服务，不另造一套提取／去重规则。
4. 打开角色详情，查看“资料检查”“表现类型”和原文依据。必要时调整宿主、表现类型与界面设计；保存仍不调用模型。
5. 对界面型系统生成或填写专用界面提示词，再明确点击生成界面图；也可上传已有界面图并确认适用。
6. 检查该系统的声线卡。界面图和声音是两份资料，界面型系统有台词时仍需要声线卡。
7. 继续分镜。后台根据已确认形态区分真实人物、可见界面与纯声音，不把系统播报写成人物嘴型或身体表演。原台词仍逐字保留。

类型待确认时先核对，不会默认给未知身份生成人像。没有可靠的旧设计依据时，外貌／妆造继续显示待完善，不凭空补一套正常人物五官或衣服。

## 3. 五种表现类型

| 类型 | 含义 | 图像处理 | 声音处理 |
| --- | --- | --- | --- |
| `person` 普通人物 | 实体人物，继续原人物流程 | 原人物提示词和形象图流程 | 按原文是否有台词检查声线 |
| `system_ui` 虚拟系统 · 界面 | 与宿主互动、以界面表达的非实体系统 | 专用界面参考图，不生成脸、人体、服装或人物三视图 | 保留同一角色 ID、原台词和声线，通常作为画外发声 |
| `avatar` 具象虚拟化身 | 原作明确的精灵、动物、机器人等具体形态 | 按已确认形态设计，不默认变成真人 | 保留该身份的原台词和声线 |
| `voice_only` 仅声音 | 明确只需声音的来源 | 不要求形象图，不把其旧人像作为视频参考 | 按原文保留播报／旁白身份和声线 |
| `pending` 待确认 | 来源或形态证据尚不足 | 不默认出人像，等待确认 | 保留身份，具体发声要求待核对 |

开启系统模式后，“系统在脑海里说话，原文没有画面描写”不自动等于“仅声音”。明确的宿主系统默认可设计界面形象；没有原文可视证据时采用观众可见的屏幕叠加层，不改人物是否看见系统的剧情事实。原文明示宿主可见才采用宿主私有视野，明示众人可见才采用场景全息投影。

每次播报也不一定出现完整弹窗。界面参考图用于保持视觉统一，是否显示界面由本镜剧情决定。不会自动照搬外部文章中的等级、数值、升级光效、固定秒数，或给无系统剧本增加系统。

## 4. 资料补齐如何保护已有结果

### 4.1 声线卡

按本集原文明示的说话人判断需求，而非“所有角色必须有声卡”。明确有台词且卡片确实缺失时，定向调用现有声线补齐能力；只给捕获到的目标角色写入，不把同批其他角色的已有卡片重做。

已有有效卡片保留。人工卡片内容非空但格式不符时显示待修正，不自动覆盖；未知说话人／别名没有可靠对应时显示待核对，不把“不确定”假报成“不需要”。声线卡保存继续使用原格式，未改变原输入 Schema。

### 4.2 样貌、妆造

先做确定性的缺字段检查；实际回填只能依据**当前已保存的最终生图提示词**。模型可以把其中已有设计整理为结构化样貌／妆造，但必须返回逐字证据，程序逐项校验该证据属于捕获的原提示词。

- 已有非空样貌／妆造不覆盖。
- 提示词没有可靠依据时留空并列明缺项，不新增设计。
- 回填期间提示词或资料被用户修改，迟到结果不覆盖新内容。
- 此回填属于整理同一份已采用设计，不走“修改形象后清空最终提示词”的常规编辑分支。
- 原图片、原最终提示词、声卡和图片历史保留。
- 系统界面、仅声音和待确认类型不套用普通人物的样貌／妆造必填要求；具体化身不凭空要求一套人类服装。

因此，“检查并补齐”可能调用文字模型，并不是无模型的字符串复制；它也不是一次重新提取整部剧本或重新创作空白角色设计。

### 4.3 完整性与分镜前置

单集提取与批量提取完成后均保存结构化检查报告。明确有台词却缺有效声卡、表现类型待确认、确切系统说话身份尚未登记／关联时，提示需处理，阻止相关分镜继续，避免缺资料仍全绿。单纯外貌结构缺项作为资料提示，已采用图片不因此作废。

单集实况覆盖提取与补齐的完整周期，不在提取工具刚返回时提前报全部结束；批次／单集资料待完善用对应诊断提示。资料补齐后只消解原文摘要、模式版本和兼容表现版本相符的问题，原检查报告仍保留，并另外记录问题已解决的回执。

新增只读系统说话身份检查只核对确切说话标注和宿主／任务等上下文，不造角色 ID、不按名字合并身份、不替原 extractor 新建人物。项目已有唯一同名角色但本集未关联时可指出真实 ID；不存在或有多个同名项时交回原提取流程／人工核对。

## 5. 旧图和新图的采用关系

本轮不删除旧人像、当前图片字段或历史记录。改变表现类型／界面设计后，只让不适用的图片退出当前可用参考投影：

- 新确认 `system_ui` 的旧真人图片不自动成为系统界面图。
- 角色详情能查看保留的原图片。用户确认上传／已有图确实适用于当前形态时，可以明确点击“确认当前图片为此形态”。
- 新图生成时捕获表现版本，完成后仅在版本仍一致时标记为此形态可用。迟到结果不把新设置对应的采用图覆盖掉。
- 图片兼容标记变化本身不制造一份新的表现版本。
- 从界面型改回普通人物时，也不能把旧界面图未经确认就当成人物图。

界面型系统的提示词保存在辅助表现设计中；旧 `characters.final_prompt` 保留。普通人物仍使用原最终提示词。手动保存元数据、刷新检查、查看原图均不自动出图。

## 6. 单项、批量、分镜与视频

提取后检查、生成前分类、角色形象准备、分镜前置均调用共享服务。前端单个角色与批量按钮也先判断 `voice_only`／`pending`；不会只修单个按钮而让批量继续把“系统”当成人像。

系统界面图是参考图的一种，场景和道具继续原流程。分镜只在需要显示界面的镜头提交此图；纯声音镜头不附旧人像或强行增加界面引用。视频提交前检查当前确认形态、采用图和实际参考图是否一致；错误时提示核对，不静默换图、删引用或重发付费任务。

界面型系统的普通播报按非实体发声处理，保留原声线／原词；原文明示旁白仍保留旁白。原来的禁片外字幕规则继续存在，仅在明确界面镜头的面板内部允许本镜原文短词／数值。此处是新增的系统模式条件逻辑，不等同于重写原分镜 Skill。

系统专用图片设计会沿用项目风格组合，再追加“不生成人体、人脸、服装或人物三视图”等界面约束，防止含人物的风格词把界面拉回人像。它不会改变普通人物、场景和道具的风格路径。

## 7. 并发、模式版本与重复请求

项目模式／类型修改会检查本项目正在运行的文字、图片准备、批次步骤和分类任务。暂停批次后尚未结束的当前步骤也算活动步骤；需等其结束。已异步交到即梦的历史结果不因此阻塞几天。

每批保存模式与模式版本。旧批次恢复时版本不一致会提示输入已变化，需新建批次，而不是让半批普通模式、半批系统模式。模型回调还核对原剧本、角色资料、表现版本和识别轮次，防止写入迟到结果。

分类有本进程单飞、项目协调和数据库轮次记录。同一身份已有明确分类时复用；自动识别仍待确认时不因下次点击图片或切换剧集就重新消费。手动设定不被自动分类覆盖。

服务启动调用 `recoverInterruptedSystemClassifications()`，将中断的旧运行记录标待核对，并使旧轮次回调失效；不自动重新调用模型。明确重新识别也不能绕过仍在运行的记录。

资料补齐 API 使用 UUID 请求号及捕获的剧本／角色／模型选项。连接结果不确定后，界面重查同一请求保留原请求号和原模型参数；明确“确认后再次补齐”才建立新请求。每角色／字段另有数据库运行记录，跨集重复操作不能在原请求未结时重复补卡。

此实现沿用单后端实例运行假设，没有声称已完成跨服务器 worker 集群、分布式租约或商业多节点调度。

## 8. API 与权限

接口前缀均为 `/api/v1`。所有公开读写核对当前登录用户、角色／剧集所属项目；宿主必须属于同一项目。手动设置接口不接受 Key、Cookie、模型隐藏指令或 owner 字段。

| 方法与路径 | 行为 |
| --- | --- |
| `GET /dramas/:id/system-settings` | 只读项目模式与版本 |
| `PUT /dramas/:id/system-settings` | 明确保存 `ordinary`／`system`；不调用模型 |
| `GET /characters/:id/representation` | 只读表现类型、原文依据、设计、宿主、版本、兼容图标记 |
| `PUT /characters/:id/representation` | 按当前 `version` 保存表现设置；`adopt_current_image:true` 明确确认已有图；不调用模型 |
| `POST /episodes/:id/system-classify` | 系统模式按所选文字配置识别新增身份；支持 `model`、`config_id`、`model_parameters`、`confirmed_retry`；普通模式不执行分类模型 |
| `GET /characters/:id/readiness` | 只读角色声线／形象资料、关联集和缺项 |
| `POST /episodes/:id/repair-assets` | 明确确认后定向补齐，支持 `character_ids`、所选模型参数、`client_request_id`、`retry_failed`；可能调用文字模型 |

系统形象提示词复用原角色“生成提示词”入口，根据项目模式和表现类型进入专用服务。界面上的“保存表现设置”与“生成专用形象提示词”是两个明确动作。

## 9. 辅助表与主要文件

| 辅助表 | 用途 |
| --- | --- |
| `platform_project_system_settings` | 项目模式与版本 |
| `platform_character_representations` | 表现类型、宿主、证据、界面设计、兼容图标记 |
| `platform_system_classification_runs` | 分类输入摘要、轮次、状态与失效 nonce |
| `platform_asset_completeness` | 本集当前资料检查报告 |
| `platform_asset_role_requirements` | 当前原文版本中角色是否确有发声需求 |
| `platform_asset_repair_attempts` | 每角色／字段的补齐轮次与状态 |
| `platform_asset_repair_requests` | 显式补齐请求幂等和结果 |

仅增加辅助表／辅助表的兼容字段；没有破坏性改造原人物／场景／道具表。批次设置和回执中保存模式版本、原文摘要和表现版本；原失败报告保留，后续确定补齐后另记录同源问题已消解，不篡改原模型失败历史。

主要代码入口：

- `backend/src/services/system-assets.ts`、`routes/system-assets.ts`：模式、类型、证据分类、版本／并发／权限。
- `backend/src/services/system-image-prompt.ts`、`system-rendering-context.ts`：专用形象设计、冻结表现事实和条件编译。
- `backend/src/services/asset-completeness.ts`、`voice-card-write.ts`、`routes/asset-readiness.ts`：只读检查、受控补空、幂等与诊断消解。
- `frontend/app/components/ProjectSystemSettings.vue`、`CharacterRepresentation.vue`、`CharacterReadiness.vue`：项目与角色共用界面。
- 项目素材库／单集制作父页面、提取／图片／分镜／批次接线点：调用上述共用能力，原模板保留。
