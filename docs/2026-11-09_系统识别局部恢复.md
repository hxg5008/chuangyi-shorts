# 系统识别局部恢复（2026-11-09，v4.6）

本轮处理“开启系统模式后，普通人物也一起显示待确认、批量图片准备受影响”的问题，承接 v4.4 系统模式和 v4.5 空白系统底图／本镜文字分离。没有改动原 44 份 Skill／系统提示词文件、20 个 Agent 工具输入 Schema 和 2 个主要分镜 Schema，也没有使用生产数据或真实付费模型。

## 1. 已定位的程序原因

此前系统模式对新角色统一等待分类，而分类响应按整批校验。一项分类格式／证据出错，可能影响同批其他有效结果。共享资料补齐层又会在分类抛错后立即返回，把本集所有角色都挂上分类异常，已确认普通人物也无法继续补声卡或整理原设计。

图片批次的识别前置同样采用整体等待；前置异常时，普通人物、场景和道具尚未开始便可能一起停止。资料检查还曾把待确认类型的形象字段标为“不适用”，容易让使用者误以为这些人物不需要形象资料。

这些是代码分析和隔离测试能确认的缺口。用户服务器截图上方的“图片准备失败”等提示是否完全由同一原因引起，尚没有用该服务器的具体日志、任务号和请求回执核实，不能仅凭截图认定所有错误都是此原因。

## 2. 分类结果按角色保留

本轮按实际角色分别处理结果：一个候选失败，不把其他已确认角色恢复成待确认，也不把同一错误复制到所有普通人。

- 有效分类立即按实际角色保留。
- 单项字段、证据或返回格式有问题，只报告对应待确认角色。
- 整体模型连接／JSON 返回异常会保留一次识别运行诊断，不把“请求失败”当成“全体角色都不是人物”的证据。
- 普通人物的恢复依据来自明确原文及对应的实体人物外观／行为依据，并检查是否存在系统、电子发声、化身等矛盾证据；不按姓名、样貌字段非空或角色名没有“系统”就直接判定。
- 没有可靠依据的身份仍待确认，不给它自动套用真人五官、衣服或人像出图。
- 用户人工确认的类型保留，不被自动分类覆盖。

历史错误保留在原运行记录中。当前已确认状态与历史失败是两件事，不通过抹掉历史来伪装此前没有发生过问题。

## 3. 资料补齐不再被其他候选连带停止

单集和批量提取仍经过同一共享资料检查。检查以当前实际表现类型为准：

- 已确认普通人可以继续定向补齐明确需要且确实缺失的声卡。
- 已确认普通人已有最终提示词时，仍可按逐字证据整理空白的样貌／妆造字段，保留采用图与原提示词。
- 待确认身份不进入自动人像设计，也不借补卡操作默认赋予它普通人物声线；先核对类型。
- 分类异常不再使共享服务提前退出其他可处理事项。

报告只把真实待确认角色计入 `pending_classification`，只将角色级错误归属给对应 ID。整体异常作为单条“类型识别”诊断保留，不伪造角色关联。

角色资料检查中，待确认身份的 `look.status` 为 `pending`，含义是“表现类型尚待核对，还没有判断人物形象字段要求”，不再显示“此类型不适用”。真正的界面型系统／仅声音类型仍不套用真人样貌、服装必填要求。原样貌、妆造和图片保留可查。

只读检查可展示最新同原文摘要、同模式、同表现版本下对应身份的分类原因；已经确认的普通人不会继承另一角色或旧全局识别错误。

## 4. 批量图片按素材继续

一个批次中包含普通人物、待确认系统、场景和道具时：

1. 待确认角色列入本次未提交清单，保留真实 ID、名称、原因和数量。
2. 已确认普通人物、场景、道具继续原图片路径，不因为该角色待确认而一起停止。
3. 不会为了让批次通过而把待确认身份强行改成人物，或忽略原采用图版本。
4. 批次结果明确显示部分类型待确认；已生成／已有图片数量仍按真实结果计算，不能全绿假报全部完成。

辅助结果中的 `pending_classification` 记录本批跳过的待确认角色数，图片步骤使用 `images_representation_pending` 表达局部类型问题；整个批次保留需关注状态。任务实况和看板区分这种情况与普通模型渠道失败，已成功素材不因此重新提交。

**确认类型不等于已经出图。** 旧图片批次当时确实没有为待确认项产生图片任务，之后不会自动重写成成功，也不自动重新消费。用户确认类型后，可在单项页面明确生成，或建立新的批次处理缺图；当前素材展示其真实采用图，旧批次继续保留当时跳过的历史警示。

## 5. 明确重试与防重复

普通提取／自动检查不自动重新提交结果不明的分类。资料检查中的“确认后再次补齐”只有在用户明确确认重试时，才映射到待确认分类的显式重试；已确认普通人不重新分类，也不覆盖有效或人工声卡。

单个角色的检查／补齐将该角色 ID 作为本次模型目标范围，未选中的其他待确认身份不会顺带重识别或写入。批量处理没有传单人范围时，仍处理该集需要检查的候选。目标属于真实当前集的关联才能提交，不通过名字猜测范围。

请求继续使用原 UUID 幂等与冻结模型参数机制：

- 同一请求重放，不重复调用分类或补齐模型。
- 同一 UUID 换剧本、目标或模型参数会拒绝。
- 用户明确建立新重试才允许再次请求待处理项。
- 已保存资产、原台词、已有图、旧请求和历史日志保留。

本轮没有把类型确认按钮改成隐式付费生图，也没有增加对普通项目全部角色的强制系统识别。

## 6. 与已有规则的边界

普通模式继续原流程。原角色、场景、道具提取消息、去重逻辑、分镜 Skill 与受保护 Schema 没有被此修复改写。系统模式只在原流程外处理表现身份与诊断，v4.5 的空白基础图规范、原文屏显证据和本镜自定义授权继续保留。

系统分类或批次状态恢复不能替代素材引用检查、模型权限检查、额度／限流诊断或下载恢复；这些错误仍需按其真实任务记录处理。

## 7. 验证与维护

主要维护位置：`system-assets.ts` 的按角色分类／恢复，`asset-completeness.ts` 的共享检查与定向补齐，`production-batches.ts` 的局部图片派发与结果，以及只读 readiness／看板的诊断展示。

隔离测试覆盖：分类局部错误不阻已确认人物的声卡／形象整理、错误不挂到普通人、待确认形象资料状态、混合图片批次继续处理正常人物／场景／道具、显式重试映射和 UUID 不重复调用。最终类型检查、前后端全量测试、构建与包校验以外层 `VALIDATION.json` 为准。

本轮没有读取用户服务器日志或提交真实模型。自动化证明的是程序的分类保存、目标隔离、派发、诊断和防重复行为；用户服务器的具体错误与真实模型分类效果，仍应结合对应任务日志做小范围验收。
